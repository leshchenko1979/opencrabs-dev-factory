## Phase 5 — Ship (`oc-ship`)

**`oc-ship` IS the single, exclusive ship path from commit to swapped binary (v0.4.126; manual push-to-main, manual issue-log, and manual oc-deploy sediment retired v0.4.132).**
The Editor runs `oc-ship` in one detached invocation under one chain-id — **armed in its OWN transient systemd unit, never via the harness's `background:true` auto-detach**.

**READ THE ARMED CHAIN ON THE USER BUS, OR YOU WILL REPORT A LIVE CHAIN AS DEAD** (c29 2026-11-19). `oc-ship` is armed in its own **transient user** unit, so its liveness is read with `systemctl --user is-active <unit>`. A bare `systemctl is-active <unit>` queries the **system** bus, which does not see user units at all: it answers `inactive` with rc=4 for a chain that is running and polling. A lane that reads the wrong bus concludes its chain died and re-arms, which dispatches a second gate onto the same ref and **concurrency-cancels the live one**. When `is-active` says inactive, confirm with `ps` before acting; the chain's own process is the authority, not a unit query. Measured 2026-11-19: `systemctl --user is-active at-spi-dbus-bus.service` → `active`; `systemctl is-active at-spi-dbus-bus.service` → `inactive`, rc=4; the near-miss on `oc-ship-809-164927` showed the chain plus its `oc-deploy ship --wait 2700` child alive, and the ship completed normally.

```bash
# 1. Push your branch first
git -C ~/opencrabs-wt/<task> push -u origin <branch>

# 2. Arm the chain in its OWN unit (resumes the session on finish)
systemd-run --user --unit=oc-ship-<issue>-$(date -u +%H%M%S) --collect \
  tools/ship/oc-ship --sha <commit-sha> --branch <branch> [--issue <issue-n>] \
    --test-threads 2
```

`oc-ship` executes the entire 5→swapped stretch mechanically:
1. **Leg 1 (CI Gate):** Dispatches and watches `oc-gate` (`pr-checks.yml` on your branch: fmt + clippy in `pr-gates`, then the blocking test verdict `pr-gates-nextest` — `cargo nextest run --cargo-profile ci --features <shipped set>` plus a separate `cargo test --doc` step. **The `cargo test --all-features` leg was DELETED 2026-11-20**; nextest is the verdict.) ⚠️ **The chain's DEFAULT gate is FAST, and FAST is NOT the CI-gate leg of the 4-Leg Smoke Rubric** (finding `127429e6`, cycle `20260919-c21`): `oc-ship` passes `--fast` to `oc-gate` unless `--full`/`--no-fast` is given, and `--fast` runs **fmt + clippy only, tests skipped** (`oc-gate --help`: the `--fast` line reads "fast gate (fmt + clippy only, skip tests on carrier)"). A FAST run's `pr-gates` job name carries the only visible marker (`… — FAST`) and the `pr-gates-nextest` job — the blocking test verdict — is **skipped outright** (job condition `!inputs.fast`), so a FAST run has no test step to read at all — citing that run as your CI-gate evidence leaves the smoke receipt with **no test-leg evidence at all**, the exact leg the "Presence and bookkeeping legs are never a smoke PASS" law protects. Pass `--full` when the receipt needs the test leg, or dispatch `oc-gate` yourself without `--fast`. **Exception — a pure-docs commit SKIPS this leg** (owner ruling 2026-09-12: *"We don't need the pure docs commits to pass through ci on our side."*): the definition, the tool-DERIVED `include_str!` exclusion set and the recording law are `§Docs-Only LEG1 Gate Skip` (this file). A skip is recorded as **SKIPPED** and is never a passed gate: do not cite a skipped leg as GREEN, and do not count it as a passed leg in a smoke receipt.
2. **Leg 2 (Issue Log):** If `--issue <N>` is supplied, posts the per-commit implementation comment via `oc-issue-log` automatically.
3. **Leg 3 (Fast-Forward Merge):** Fetches fork `main`, verifies fast-forwardability, and pushes `<branch>:main` (serialized via `ship.lock`).
4. **Leg 4 (Carrier Ship):** Dispatches `oc-deploy ship --sha <sha> --execute` to build on `ci/quick-build-linux`.
5. **Leg 5 (Swap & Seal):** Bounded-polls carrier execution (`oc-deploy poll --execute --wait <sec>`) until the binary is live and swapped. The ship wait default is **2700 s** (`OC_SHIPCHAIN_SHIP_WAIT` in `oc-ship`) — raised from 900 s at #336 after 11 of 37 carrier successes exceeded 900 s (10 most recent: 942-1344 s, median 1062 s). A shorter budget mislabels a still-building run as **SHIP-WAIT-TIMEOUT — `rc 8`, not `rc 6`** (`oc-ship`): rc 8 means the run is still BUILDING and must NOT be re-dispatched, while rc 6 is a poll verdict on a run that already reached a terminal state.

**Carrier Coalescence & Ancestry Matching (v0.4.148):** editors do not serialize on a
pre-dispatch carrier lock — descendant builds are accepted via ancestry matching, host swaps
stay serialized and monotonic via `host-swap.lock`. Full law: `§Carrier Concurrency & Coalescence Law` (this file).

There is NO legitimate manual exit point between gate verdict and swap. The #134 orphan class (stopping at GREEN without swapping) is structurally closed.

When shipping features via `oc-ship` or deploying via `oc-deploy`, failures and interruptions follow the mechanical automation vs. manual resolution contract below:

**Exit codes & Lane action:**
- **Exit 0 — SWAPPED:** The new binary is running live on the host (`opencrabs-ops` user unit). Worktree can now be removed (`tools/git/oc-wt remove <task>`). Proceed immediately to Phase 6 (Smoke-test-on-notify).
- **Exit 2 — USAGE:** Bad or missing arguments (`--sha`/`--branch` are required; malformed flag). Correct the invocation and re-run — no lane state to resolve.
- **Exit 3 — DIRTY CHECKOUT:** The fork checkout has uncommitted changes (pre-flight refusal). Clean or stash it, then re-run.
- **Exit 4 — GATE-RED / CARRIER-RED:** The CI gate failed or the carrier build failed. Start a fix round (Phase 6-Fix): keep the same branch, fix in a new worktree, commit, push, and re-run `oc-ship`. Triage heuristics: `editor.md §Red-run triage heuristics`. **Also the `--gated-run` / `--gated-sha` pre-verify failure:** the supplied run was not `completed success` on a job pinned to the sha, or `--gated-sha` did not match `--sha`. Do NOT re-dispatch the run — re-verify it with `gh run view <id> --json status,conclusion,jobs` and re-supply the correct id.
- **Exit 5 — NON-FF / MERGE CONFLICT · TIP-MOVED · REBASE-GATE:** EIGHT distinct causes share this code, enumerated in `oc-ship`'s own header from `grep -c 'die ".*" 5$'` (NON-FF, STALE-BASE, TIP-MOVED, REBASE-GATE, ALREADY-LANDED, LOCAL-MAIN-DIVERGED, LOCAL-MAIN-AHEAD, STALE-LOCAL-MAIN); full register in `tools/docs/RC-CONTRACT.md`. Three are detailed below; the other five name themselves in the tool's message. **(a) NON-FF / MERGE CONFLICT** — `oc-ship` LEG3 ran `git merge --ff-only` and refused. A **clean** non-FF and a **conflicted** one are the SAME code from the chain's side: the chain performs **no rebase of its own**, so the LANE rebases `$BRANCH` onto fork main and force-pushes first; a **semantic conflict** additionally requires hand adjudication. (Cause **(c)** is `oc-deploy`'s own auto-rebase — do not wait for one the chain never runs.)
  ```bash
  git -C ~/opencrabs-wt/<task> fetch origin
  git -C ~/opencrabs-wt/<task> rebase origin/main
  # resolve conflicts in working tree
  git -C ~/opencrabs-wt/<task> push --force-with-lease origin <branch>
  ```
  ⚠️ **`oc-rebase-safety` is NOT the rebase engine** — it is a READ-ONLY safety auditor (`audit` / `overlap`). Use standard git commands to resolve conflicts, verify zero lost edits with `oc-rebase-safety audit`, and re-run `oc-ship`.
  - **(b) TIP-MOVED** — the branch was force-pushed mid-gate, so `$TIP != $SHA`: LEG3 refuses rather than fast-forwarding fork main onto a tip NO GATE VALIDATED. Recovery: re-run the chain against the new tip — do NOT land the ungated tip.
  - **(c) REBASE-GATE** — `oc-deploy`'s in-tool auto-rebase refused the push (`OC_DEPLOY_GATE=rebase-conflict` / `rebase-audit-failed`). Recovery: rebase `$BRANCH` onto fork main yourself, verify with `oc-rebase-safety audit`, then re-run.
- **Exit 6 — INFRA:** dispatch or poll infrastructure failure (`oc-gate` rc 4/7/8, or ship rc other). **A LEG5 `rc=6` is NOT automatically a failed ship — read its three evidence fields before you act (#85):** the message carries (a) `oc-deploy`'s own wrapped diagnosis (`POLL_CAUSE` — the **whole set** of `oc-deploy: ` lines joined ` | `, never just the first: a cause may appear in any element, and the first may name none), (b) `leg5_host_state()` = `deployed.sha` + the installed binary's sha256 + whether it matches `deployed.meta.artifact_sha256`, and (c) a `<HINT>` chosen from what poll actually reported. **If the cause names `gh api`/`API` (rc 2), the API was unreadable, not the ship** — the binary may already be live and verified, so re-run `oc-deploy poll --execute` and do **NOT** re-run the chain. Any other cause keeps the user-bus hint (a chain armed as a system unit does not have it). Before #85 the hint named the user bus for EVERY poll failure, so an API blip sent lanes hunting infrastructure that was fine. ⚠️ **NOT the UNSIGNED case, and NOT a post-push ORDER-gate rejection:** an unsigned head commit is caught **BEFORE the merge** and exits **3**; a post-push ORDER-gate rejection exits **4**. Both are this section's neighbours, not infra: a head commit carrying no `Session-Id` trailer is refused by ORDER gate 4 (`oc-verify-order: UNSIGNED … attribution mandatory`). Read the message before you act — if it says UNSIGNED, do not go hunting for a network or carrier problem. Fix = land an empty trailer-signed marker commit on the head (tree-identical, forward-only; `upstream-merge-runbook.md` step 9) and re-run. Every synthesis/merge head is unsigned **by construction**, so this recurs on every sync. **A lineage-guard refusal ALSO exits 6** (`non-monotonic-swap`): the guard is rebase-aware (v0.4.151) and accepts the swap as `rewrite-equivalent-swap` — recovery is **re-run the same leg** — **NEVER hand-edit `deployed.sha`** (`§Post-Rewrite Swap Recovery`). ⚠️ **A gate CANCELLED with no verdict is NOT "a gate that already ran" — find the live run before you dispatch (#93, `CANCEL_CLASS=SELF_CANCEL`).** The rc 6 remedy above says *do NOT re-dispatch a gate that already ran*: correct for `SUPERSEDED`, where a later run pins your sha and the recovery is to resume it — **INVERTED for a self-cancel**, where the run exists but reached no verdict, so the sha is UNGATED and something must still gate it. The order matters because `pr-checks.yml` keys its concurrency group on `prchecks-${{ inputs.ref }}`: **a dispatch onto that gated ref CANCELS whatever is live on it, so the re-dispatch is itself the canceller.** Neither obvious shortcut is dispatch-free — `oc-gate wait <ref>` only changes budget/poll and still dispatches, and adoption runs AFTER the dispatch so it can find the run your dispatch just created but cannot protect one already in flight. The only dispatch-free verb is `resume <id>`, and it needs a numeric run id. The chain does NOT auto-re-arm this class (`chain_rearm_action` re-arms rc 6 only on a NUMERIC `GATE_SUPERSEDING`, so a self-cancel lands on the `norearm-gate-infra-6-cancelled` arm) — the lane owns the recovery, in this order: **(a)** read the actor the receipt names (`cancelled deliberately by a caller @<handle>`); **(b)** look for a run already gating YOUR sha — `gh run list --workflow pr-checks.yml -R <repo> --limit 30`, then read each job name for `PR-lane gates (<sha>)` — and if one exists and is not terminal, `oc-gate resume <id> --wait <sec>` and do NOT dispatch; **(c)** re-dispatch ONLY if no run gates your sha AND that sha is still your branch tip; **(d)** if the branch has moved, do nothing — the gate is obsolete, and a gate is dispatched only if one is still needed; **(e)** a second cancel by the SAME actor is a decision, not a flake — stop and escalate, because a third dispatch is noise.
- **Exit 7 — GATE IN FLIGHT:** the gate was still running after the chain's budget and resume-polls (`oc-gate` rc 5, non-terminal). The run id is printed — do **NOT** re-dispatch (that concurrency-cancels the live run); wait for it and re-run with `--gated-run <id>`, which pre-verifies and skips dispatch.
- **Exit 8 — SHIP-WAIT-TIMEOUT:** the carrier build did not reach a terminal state within the LEG4 `--wait` budget (default 2700 s; `oc-deploy ship` rc 5 with no rebase-gate token). ⚠️ **The run is still BUILDING — do NOT re-dispatch it** (a re-dispatch concurrency-cancels the live run). Wait for it, then resume with `oc-deploy poll --sha <sha> --execute --wait <sec>`, or re-run the chain with a larger `--wait`. This code exists precisely because the Exit 4/6 reflex ("re-run the chain") is the double-dispatch this arm prevents.

**Conflict-quality gate — MANDATORY after any rebase with hand-resolved code:**
*(A hand-resolved merge shipping a crate-alias mismatch is five E0308s and a red CI round-trip)*:
1. Re-read every hand-merged function END-TO-END — not just the conflict hunk.
2. Match crate-wide type aliases: open the alias definition; the error type is usually locked by the alias.
3. Grep the tree for duplicate imports and doubled tests the resolution may have left behind.
4. **Prove nothing was lost** (finding `6cd8175f`, cycle `20260919-c21`): `git diff <new-base> HEAD --stat` must list ONLY files this branch changed. `oc-rebase-safety audit` cannot settle this after a rebase onto a MOVED main — every file both sides touched reports `CHANGED` (main's own edits sit inside `C..B`, where `C = merge-base(A,B)`), so their patch-ids can never match `C..A`, and the SUMMARY line then reads `LOSSES FOUND — full re-gate required` even when zero content was lost. Read the audit's **`DROPPED`** rows as the loss signal; treat **`CHANGED`** as indeterminate and confirm with the diff. A lane that trusts the summary hunts a loss that does not exist.

**Post-landing-lock ancestor re-check — MANDATORY before LEG3 lands (finding `127429e6`, cycle `20260919-c21`):** the gate (LEG1) runs BEFORE the landing lock is taken, so the window between "gate green" and "lock acquired" is unprotected — and LEG3 is a bare `git merge --ff-only` that performs **no rebase of its own**. Any lane landing on fork `main` inside that window makes your branch a non-fast-forward and LEG3 dies `rc 5` (cause **(a)** above). **A chain queued on `ship.lock` is already doomed if `origin/main` moved while it waited** — it will take the lock and then refuse. After acquiring the lock, re-check ancestry against the CURRENT remote tip:

```bash
git -C ~/opencrabs-wt/<task> fetch origin
git -C ~/opencrabs-wt/<task> merge-base --is-ancestor <branch> origin/main || {
  git -C ~/opencrabs-wt/<task> rebase origin/main      # hand-resolve any conflicts
  git -C ~/opencrabs-wt/<task> push --force-with-lease origin <branch>
}
```

⚠️ **Distinguish this from the v0.4.214 local-main reconcile — same `rc 5`, opposite fixes.** v0.4.214 covers LOCAL `main` being stale while the branch is *correctly* based on `origin/main`: that is a FALSE alarm and the fix is **do not rebase**. This check covers `origin/main` having genuinely MOVED during the gate: the rebase is **real and necessary**. The v0.4.214 diagnostic (`git merge-base --is-ancestor main origin/main`) does not separate the two — test against `origin/main`, never against local `main`. Automating the re-check inside the chain (pre-LEG3) is a Toolsmith call; until it lands, the LANE owes the check.

## Rebase discipline — ONCE, at ship time (never mid-development) [LANE]

**The rule.** A lane rebases `$BRANCH` onto fork `main` **only at ship time**: the single rebase immediately before `oc-ship`, or the recovery rebase an exit-5 NON-FF forces (§Failure Modes cause (a)). **Never mid-development**, and never as a periodic "stay current" hygiene step. Commits land on the branch as they are; the branch is allowed to sit behind `main` for the whole development arc.

**Why — a replay does not MOVE commits, it REPLACES them.** Every rebase re-writes each replayed commit under a new sha. Everything the lane recorded against the OLD shas goes stale in one operation, and none of it announces the break:

| receipt recorded before the rebase | what the replay does to it |
|---|---|
| `deployed.sha` ancestor checks (`git merge-base --is-ancestor <commit> <deployed>`) | the old sha leaves the branch's history, so the check answers NO for work that IS deployed |
| `Issue-Ref` / `Session-Id` trailers | survive as text but now name a sha that exists on no remote |
| a `CHANGELOG`, ledger or issue comment citing a sha | same: the cited sha is unreachable, so no later reader can verify the citation |
| `smoke-verdicts.log` PASS rows | a verdict taken on the pre-rebase tree no longer names the tree that ships |
| the harvest ancestor-walk (`oc-harvest-dispatch`) | it matches ported commits by walking the range; a replay changes every patch's identity, so a ported commit can no longer be matched to its re-sha'd twin |

**And the trailer loss is silent.** `fleet-directives.md §Swap-head signature for rebase/synthesis/merge-derived binaries` clause 4: rebase, cherry-pick and filter operations can STRIP `Session-Id` and `Issue-Ref` trailers, and the check is the TOOL (`oc-attrib --trailers-only --range <A..B>`), never a hand parse. A mid-development rebase performs that rewrite before there is any reason to, so the verification cost is paid repeatedly instead of once.

**Measured churn this rule exists to stop:** 51 rebases box-wide, **147 commit subjects replayed 2+ times**, and the worst case (`chore/875-rebase`) picked the same 5 dependency commits **5 times each**: 25 replays minting 25 sets of shas for 5 logical changes.

**What a lane does instead:** leave the branch alone and keep working. A moved `main` is not an emergency — the ship-time rebase handles it, and LEG3's `--ff-only` refusal at ship time is the DESIGNED signal to rebase then. If a conflict genuinely blocks (a file you must edit has moved under you), rebase once, immediately, and re-take every receipt that named an old sha. Do not make it a habit, and do not rebase "to keep CI honest": the gate runs on the tip, whatever its base.

## Docs-Only LEG1 Gate Skip (v0.4.161, owner ruling 2026-09-12 11:04Z) [LANE]

**Owner ruling (verbatim, 2026-09-12 11:04Z):** *"We don't need the pure docs commits to pass through ci on our side."* Origin: a lane's docs-only commit burned LEG1 in full before the ruling landed.

- **The law.** A commit whose changed paths are ALL **pure docs** SKIPS the LEG1 CI gate on the fork ship chain. A skip is neither PASS nor RED — it is a **SKIP**, and it MUST be recorded as one in the ship chain journal, never left implicit.
- **"Pure docs" is DEFINED HERE, never left to a tool's discretion.** A commit is pure docs iff **every** changed path (a) ends in `.md` **and** (b) is **NOT compiled into the binary** via `include_str!` / `include_bytes!`. Clause (b) is load-bearing: a `.md` compiled into the binary changes COMPILED OUTPUT, so touching it is a code change and MUST run the gate. A chain shipping a RANGE needs every commit in the range to be pure docs.
- **The exclusion set is DERIVED BY THE TOOL at gate time — never by hand, never carried in a lane's context.** Any such path list is **illustrative, not normative**: it rots the moment a template is added or removed, and a lane reproducing it by hand is the defect this clause prevents (owner: *"that should be purely mechanical"*). The gate resolves the compiled-in `include_str!` targets against `src/**/*.rs` at run time; lanes verify with `tools/ship/oc-ship --eval-docs-skip <sha>` (Finding J-2, v0.4.170).
- **Recording is MANDATORY — an absent gate is NEVER a passed gate.** A skipped LEG1 MUST be recorded in the ship journal **and** in a `shipchain` ledger row naming the sha, the leg stated as SKIPPED. GREEN may be stated only for a gate that actually ran and returned `completed success`; a skip is cited as SKIPPED, never GREEN, and never counted as a passed leg in a smoke receipt.
- **Enforcement split.** The law text is HQ's (this section); the mechanical LEG1 behaviour is Toolsmith's and LANDED in `d6cb9b9a` (v0.4.161): pure-docs commit SKIPS LEG1, the exclusion set is DERIVED at gate time (`shipchain_docs_only()` — cite by function name, never by line), the skip is journalled (`GATE-SKIPPED-DOCS`) plus a `shipchain` ledger row, it applies to a FRESH dispatch only (`--gated-run`/`--gated-sha` still gate), and `OC_SHIPCHAIN_NO_DOCS_SKIP=1` forces the gate. Upstream's `**.md` / `docs/**` paths-ignore shape is deliberately NOT copied — it would skip a commit editing a compiled-in template. Never claim a skip the tool has not recorded.

## Post-Rewrite Swap Recovery (v0.4.151, Toolsmith brief 2026-09-12) [LANE]

**After a fork-main rebase, RE-RUN the same `oc-ship` leg — never hand-edit `deployed.sha` to re-point around a refusal.**

A rebase orphans the deployed sha (it stops being an ancestor of `main`), and the pre-v0.4.151 guard refused **every** such swap with `non-monotonic-swap`. The guard is now rebase-aware: when the incoming lineage carries the deployed change under a new sha (patch-id match) it journals `rewrite-equivalent-swap` with the twin sha and admits the swap. A guard refusal surfaces as **`rc 6`** from `oc-ship`; the recovery is a re-run, not a marker edit.

`oc-deploy lineage-check --prev <deployed> --sha <incoming>` returns the verdict (`ok` / `rewritten` / `absent`) read-only, without touching gate state. Re-pointing `deployed.sha` by hand leaves a false audit trail for a sha that was never built as a run and is **prohibited** (HQ ruling 2026-09-12, lane `2fbfb2f8` incident). A genuinely-absent change refuses until the audited `--allow-rewritten-lineage` override is passed with a mandatory justification.

## Carrier Concurrency & Coalescence Law (v0.4.148, Toolsmith brief 2026-09-12) [LANE]

- **Concurrency semantics:** `ci/quick-build-linux` runs under `concurrency: group: quick-build-linux` with default queuing (1 active + 1 pending; further dispatches cancel and replace the pending run). Editors push to `origin/main` immediately — no pre-dispatch carrier lock.
- **Coalescence:** `oc-deploy` and `oc-ship` accept descendant builds by ancestry matching (`git merge-base --is-ancestor "$SHA" "$CAND_SHA"`), so pushes landing while a build runs coalesce into one build and every contributing editor recognises its commit as deployed without a redundant dispatch.
- **Host swap mutex:** host binary swaps stay strictly serialized and monotonic via `host-swap.lock` (`flock -x $STATE_DIR/host-swap.lock`) plus lineage verification — a stale binary cannot overwrite a newer one.
- **Merge serialization:** `oc-ship` serializes Leg 3 (fast-forward merge) via `ship.lock`.

## Features-compat gate — no silent feature-loss swaps (HQ ruling 2026-09-04, MANDATORY) [LANE]

`oc-deploy swap-execute` **refuses** any artifact whose feature set drops a feature present in `deployed.meta.json` (exit 4, journal `features-drop-gate`, markers untouched) unless `--allow-features-drop` is passed explicitly. Feature *additions* pass freely; *drops* are the failure class. Enforced in-code (selftest 17p/17q). Rationale: the 06:36:06Z rogue swap (run `33844429519`, `features="telegram"` over a live `telegram,code-graph` binary) killed structural memory for 12h, and the 18:57Z f3c03269 swap was the same class. The gate would have refused both.

## Abort & safety levers (`oc-deploy`) [LANE]

A ship that must be stopped is stopped HERE, not by killing a PID — every lever below is read by the tool itself, before it does anything.

- **Kill file aborts EVERY invocation, selftest included** (exit 9, checked first): `$STATE_DIR/oc-deploy.kill` or `${HOME:-/root}/oc-work/oc-deploy.disabled`. Touch either and every `ship` / `poll` / `swap-execute` / `fanout` refuses; remove it to re-arm. This is the only abort that survives a restart and reaches a run already dispatched.
- **Plan-only UNLESS `--execute`.** Without the flag nothing is dispatched, nothing is swapped: every action prints as `PLAN: ...`. Plan mode always prints its full delta — it never exits 0 silently, so "no output" means the invocation died, not that there was nothing to do.
- **Swap actions require stage ≥ S2** (`poll --execute`, `swap-execute`). Below S2 they refuse rather than degrade.
- **Shadow journal** `$STATE_DIR/oc-deploy-shadow.log` records every run, plan or execute — the first place to look when you cannot tell whether an invocation happened.
- **Consent gate RETIRED 2026-08-28** (owner order): a GREEN carrier run plus artifact verify IS the authorization. Post-SMOKE-FAIL rollback stays the owner's call.
